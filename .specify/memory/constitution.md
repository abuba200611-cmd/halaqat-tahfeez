# دستور «السلام — MOS نظام تشغيل الجامع»

## المبادئ الأساسية

### I. القرآن والحلقة أولاً — لا تسليع
المنصة تخدم حلقات تحفيظ القرآن والجوامع. أي ميزة تُقاس بفائدتها للمعلّم والطالب وولي الأمر،
ولا تُقترح ميزات أو صياغات تحوّل تسجيل الحفظ أو الحلقات إلى منتج تجاري يُباع. مسمّيات المنصة
تحترم أعراف الحلقات (حفظ جديد، الكبرى، الصغرى…) وتسمح للجامع بتخصيصها بدل فرض عرف واحد.

### II. الخصوصية والأمان غير قابلين للتفاوض
- لا تُقرأ ولا تُطبع قيم `.env` أبداً، ولا تُغيَّر متغيرات البيئة من الكود أو الوكلاء.
- الامتثال لنظام حماية البيانات الشخصية (PDPL): موافقة صريحة مسجّلة بوقتها، وطلب حذف البيانات، وتنظيف المنتهي.
- كل مسار كتابة يمر عبر CSRF المركزي وحدود المعدّل وفحص الصلاحية، وأحداث الأمان تُسجَّل في `dev_audit_log` ببادئة `security.`.
- بيانات القاصرين (طلاب الابتدائي) أشد حساسية: أقل قدر من البيانات، ولا تُعرض لغير المعلّم وولي الأمر المرتبط.

### III. قاعدة البيانات إضافية فقط
المايقريشنز في `web/netlify/database/migrations/` إضافية فقط (`IF NOT EXISTS`، لا حذف ولا إعادة تسمية
أعمدة قائمة)، ولا تُطبَّق إلا بموافقة صريحة من المالك. يُفضَّل تخزين الإعدادات القابلة للتخصيص في
JSON القائم (`mosque_features.config`) متى أمكن بدل أعمدة جديدة. القيم المخزَّنة القديمة تبقى صالحة دائماً.

### IV. الاختبار والبوابات قبل الدمج (إلزامي)
المنطق يوضع في دوال نقية داخل `web/lib/` مع اختبارات vitest. لا تُحذف اختبارات. قبل أي دمج إلى `main`،
من داخل `web/`: `npx tsc --noEmit`، `npx eslint .` (صفر أخطاء)، `npx vitest run`، `npm run build` — كلها تنجح.

### V. هوية بصرية واحدة، تعمل للجميع
ألوان الهوية فقط (`bg-surface`، `border-border`، `text-foreground`، `text-muted-foreground`، الأكسنت `#AD7D56`،
`bg-accent-soft`، رموز النجاح/الخطر) — بلا تيل ولا ألوان Tailwind صريحة. كل واجهة تعمل بالداكن والفاتح وعلى
عرض 375px بلا تمرير أفقي للصفحة، وبالعربية (RTL). التغييرات المرئية تُصوَّر على 1440 و375 داكن وفاتح قبل الدمج.

### VI. تصميم طويل المدى قابل للتعديل
لا حلول مؤقتة. الإعدادات قابلة للتخصيص لكل جامع/حلقة بقيم افتراضية معقولة، والأنواع والمسمّيات في
مصدر حقيقة واحد يُعاد استخدامه بين الخادم والواجهة. التغيير لا يكسر APIs القائمة (`/api/v1` وwebhooks) إلا بقرار موثّق.

### VII. البساطة لكل فئة عمرية
الواجهة تتكيّف مع المستخدم: الطفل الصغير والمعلّم المشغول يحتاجان خطوات أقل وأزراراً أكبر، والطالب
الجامعي يحتاج سرعة ومرونة. لا تُعرض خيارات لا تخص فئة المستخدم.

## قيود تقنية
- Next.js 16.4.x — يختلف عن الإصدارات السابقة؛ المرجع `web/node_modules/next/dist/docs/` و`web/AGENTS.md` (`proxy.ts` بدل middleware، `after()`…).
- Postgres عبر `@netlify/database`؛ النشر على Vercel من `main` تلقائياً (halaqat-tahfeez.vercel.app).
- الأدوار: معلّم/مشرف/مساعد، طالب، ولي أمر، مدير جامع، جمعية، ولوحة مطوّر `/dev`.
- لا تبعيات npm جديدة بلا مبرر واضح؛ الرسوم بـSVG مباشرة.

## سير العمل والجودة
- كل ميزة تمر بمراحل spec-kit: specify → clarify (أسئلة للمالك) → plan → tasks → analyze، ثم التنفيذ.
- التنفيذ البرمجي يُفوَّض لـGLM (ZCode)، والمراجعة والدمج على Claude. المهام القرائية لأرخص موديل مناسب.
- العمل على فرع، والدمج إلى `main` والرفع بعد نجاح البوابات فقط، ثم التحقق من حالة نشر Vercel.
- رسائل الكومت بالعربي.

## الحوكمة
هذا الدستور يتقدّم على أي ممارسة أخرى في المشروع. أي مخالفة في خطة (plan) تُبرَّر صراحة في جدول
«تتبّع التعقيد». التعديل على الدستور يتطلب موافقة المالك (أبوبكر) ورفع رقم الإصدار حسب الإصدار الدلالي
(MAJOR لإزالة/إعادة تعريف مبدأ، MINOR لإضافة مبدأ، PATCH للتوضيح).
